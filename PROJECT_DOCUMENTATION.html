1. Project Overview

AI Detective: The Missing Developer is a full-stack AI-powered detective game. You play as an intern at a software company whose lead developer — Alex Mercer — has mysteriously disappeared. You investigate their workstation, collect evidence, interrogate AI-powered suspects, and make a final accusation.

What makes this project portfolio-worthy

  • Characters are powered by GPT-4o — they respond dynamically, remember context, and reveal secrets only when confronted with the right evidence
  • Evidence has a progressive unlock chain — collecting one clue unlocks the next, creating a real investigation feel
  • Full REST API + WebSocket backend with session management and conversation persistence
  • Every conversation is stored in MySQL — you can replay any session
  • The story involves real software concepts: git commits, production server logs, data breaches, GDPR violations

Alex Mercer, the lead developer at Nexus Corp, discovered that the company was secretly selling user data to a third-party broker called DataBridge Solutions — earning $102,000 per month in violation of GDPR and the company's own privacy policy.

When Alex tried to report this internally, they were shut down. Dana Voss (CEO's assistant) ordered Sam Carter (DevOps) to delete Alex's monitoring scripts at 2AM, revoke their access, and fabricate an HR performance review. Alex was escorted out under an NDA.

4. Frontend Deep Dive

State Management — GameContext.jsx

The entire game state lives in a single React Context powered by useReducer. No Redux needed — the state shape is simple and predictable.

{
  sessionId: "abc123",           // from backend when game starts
  playerName: "Akhila",
  phase: "investigation",        // controls which screens are accessible
  collectedEvidence: ["git_001", "note_001"],  // IDs of found clues
  interrogated: ["jordan_lee"],  // which suspects have been talked to
  conversations: {               // full chat history per suspect
    "jordan_lee": [
      { role: "player", text: "Where were you?", timestamp: 1234 },
      { role: "character", text: "I was at my desk...", timestamp: 1235 }
    ]
  },
  notes: [{ id: 1, text: "Sam was up at 2AM" }],
  elapsed: 823,                  // timer in seconds
  accusation: null               // set when player makes final accusation
}

Screen Breakdown

IntroScreen.jsx

Displays a CRT-style boot sequence using setInterval to reveal lines one by one with useState. After all lines show, a form appears. On submit it calls POST /api/sessions/start and dispatches START_GAME. If the backend is down it still works — falls back to a local session ID so the frontend is always playable.

InvestigationScreen.jsx

Three-panel layout: left sidebar (folders + suspects), middle (file list + file content), right (notes). Uses the getAvailableEvidence(collectedIds) function from evidence.js to filter which files appear based on what the player has already collected. Clicking a file dispatches COLLECT_EVIDENCE and shows the content + analysis. Has a live timer using useEffect + setInterval dispatching TICK every second.

InterrogationScreen.jsx

Chat UI. When the player sends a message it: (1) dispatches the message to state, (2) calls POST /api/interrogate with the full conversation history, (3) shows a bouncing "thinking..." animation, (4) dispatches the AI reply to state. The player can also click "Present Evidence" to show a collected clue to the suspect — this formats the message as "I want to show you something. [Presents evidence: Alex's Draft Email]" which the AI picks up on and responds to in character.

EvidenceBoardScreen.jsx

Renders each collected evidence item as a "pinned card" at predefined positions with slight random rotations to simulate a real detective cork board. Uses Framer Motion for staggered entrance animations. Clicking a card shows its full content and analysis in the right panel.

AccusationScreen.jsx

Player selects a suspect, picks a motive from a dropdown, and optionally selects supporting evidence. Has a two-step confirmation to prevent accidental submissions. Calls POST /api/accuse and dispatches RESOLVE_CASE based on whether the backend says the accusation is correct.

OutcomeScreen.jsx

Shows win or lose state. Uses TypewriterText component to reveal the full narrative of what happened. Displays stats: evidence collected, suspects interrogated, time taken. Has "Play Again" which dispatches RESET and navigates back to intro.

Service Layer Explained

OpenAiService.java

Uses Spring WebFlux's WebClient to call the OpenAI Chat Completions API. Builds a JSON body with the model name, temperature, max tokens, and an array of messages (system prompt + conversation history). Parses the response JSON to extract choices[0].message.content. Throws a RuntimeException if the API call fails so the controller can return a 500 error to the frontend.

CharacterRegistry.java

An in-memory @Component that holds the LLM system prompt for each of the 4 suspects. Each prompt defines the character's personality, their secrets, and how they should behave at different stages of interrogation (evasive at first, revealing under pressure). This is the most important part of the AI design — the quality of responses depends entirely on how well these prompts are written.

InterrogationService.java

The core AI orchestration service. It: (1) validates the character ID, (2) persists the player's message to MySQL, (3) builds an enriched system prompt that includes what evidence the player has collected so far, (4) limits conversation history to the last 10 turns to control token costs, (5) calls OpenAiService, (6) persists the character's reply to MySQL, (7) returns an InterrogateResponse DTO.

EvidenceRegistry.java

Server-side mirror of the frontend's evidence.js. Validates that evidence unlock prerequisites are met before recording a collection. For example, you can't collect the "Encrypted File" unless you've already collected "Alex's Sticky Note". This prevents cheating by directly calling the API.

AccusationService.java

Reads the culprit ID from application.properties (game.culprit-id=dana_voss). Compares it to the accused ID. Calls SessionService.recordAccusation() to persist the result. Returns an AccuseResponse with correct=true/false and a full explanation of what happened.

7. AI / LLM Integration

How the AI Characters Work

Each character has a system prompt — a detailed set of instructions given to GPT-4o before every conversation. The system prompt tells the AI:

  • Who the character is (name, role, personality)
  • What their secrets are
  • How they should behave when questioned
  • When to reveal information and when to hide it
  • What happens when specific evidence is presented

Example — Dana Voss System Prompt (simplified)

You are Dana Voss, Executive Assistant to the CEO of Nexus Corp.
You are polished, cold, and calculating. You never lose composure.

Secrets:
- You orchestrated Alex Mercer's removal from the company
- You ordered Sam Carter to delete monitoring scripts at 1:47 AM
- You forged the HR performance review retroactively
- DataBridge Solutions deal = $102K/month. You protect it at all costs.

Behaviour:
- Always calm, slightly patronizing toward the intern
- If confronted with your email to Sam: "that email is being taken out of context"
- Only if confronted with ALL key evidence: "I'd advise you to be very careful
  about what you think you know."
- Never admit wrongdoing. Never apologize.
- Respond in 2-3 sentences, icy and composed.

Context Injection — Making AI Smarter

Every time the player asks a question, the backend enriches the system prompt with what evidence the player has collected:

--- GAME CONTEXT ---
The player is: Akhila (an intern).
Evidence the player has collected so far:
  - Dana Voss Internal Email [email]
  - Server Access Log — Oct 14 [log]
  - Alex's Draft Email (Unsent) [email]

This means Dana Voss will respond differently if the player has her email versus if they don't. The AI dynamically adjusts — getting more defensive when cornered with hard evidence.

Token Management

  • Max tokens per response: 300 (keeps responses concise, in-character)
  • Temperature: 0.85 (creative but not random)
  • Conversation history limit: last 10 turns (prevents token overflow on long interrogations)
  • Model: GPT-4o (best balance of quality and speed)

11. Interview Questions & Answers

These are real questions interviewers will ask about this project. Read these carefully — knowing your own project deeply is what impresses them.

🔵 General / Project Questions

Q1. Tell me about this project. What does it do?
It's a full-stack AI-powered detective game called "The Missing Developer." You play as an intern investigating the disappearance of a lead developer at a tech company. You explore their workstation — git commits, emails, server logs — collect evidence, and interrogate four suspects who are powered by GPT-4o. Each suspect responds dynamically based on what evidence you've collected. At the end you make a final accusation. The story involves a real software scenario: a data breach where user data was being secretly sold to a third party. I built it with React on the frontend, Spring Boot on the backend, MySQL for persistence, and the OpenAI API for the AI characters.
Q2. Why did you build a game instead of a standard CRUD app?
I wanted to showcase AI integration in a way that's actually interesting — not just a chatbot, but a system where the AI's responses change based on game state. A detective game naturally required multiple connected systems: state management, a REST API, database persistence, real-time WebSockets, and LLM integration. It's more complex than a to-do app and demonstrates that I can architect systems where multiple technologies work together. It also shows I can write compelling system prompts — which is a real skill in AI product development.
Q3. What was the hardest part to build?
The hardest part was making the AI characters behave consistently and realistically. Just giving GPT-4o a character description wasn't enough — I had to engineer the system prompts carefully, inject dynamic context about what evidence the player had collected, and tune the temperature and max tokens to get responses that felt natural and in-character. I also had to decide how much to reveal at each stage of interrogation, which required testing many different prompt strategies. The progressive evidence unlock chain was also tricky — I mirrored the same unlock logic on both frontend and backend to prevent cheating via direct API calls.

🟢 React / Frontend Questions

Q4. Why did you use useReducer instead of useState for game state?
The game state has many interconnected pieces — phase, collected evidence, conversation history, interrogated suspects, notes, and a timer. With useState I'd have a dozen separate state variables and complex update logic scattered across components. useReducer centralises all state transitions in one reducer function with named action types like COLLECT_EVIDENCE or RESOLVE_CASE. This makes state changes predictable, testable, and easy to debug. It's essentially Redux pattern without the extra library.
Q5. How does the progressive evidence unlock work on the frontend?
Each evidence item in evidence.js has an unlockAfter array — a list of evidence IDs that must be collected before this item appears. The getAvailableEvidence() function filters all evidence items by checking whether every ID in unlockAfter exists in the player's collectedEvidence array. This runs on every render of the Investigation screen, so the UI automatically shows new files as soon as prerequisites are met. The same logic runs on the backend in EvidenceRegistry.java to validate API calls independently.
Q6. How does routing and access control work?
I use React Router v6 with a custom ProtectedRoute component that checks the current game phase from context. Each route declares which phases are allowed to access it. For example, /interrogate/:id requires the phase to be investigation or interrogation. If you try to navigate to /outcome before solving the case, ProtectedRoute redirects you back to the intro screen. This prevents players from skipping to the end.
Q7. How does the Vite proxy work? Why is it needed?
During development, React runs on port 3000 and Spring Boot on port 8080. If the frontend directly called http://localhost:8080/api, the browser would block it due to CORS policy — requests from one origin to another are blocked by default. The Vite proxy in vite.config.js intercepts any request starting with /api and forwards it to port 8080 server-side, making it appear same-origin to the browser. In production you'd configure NGINX or a load balancer to do the same thing.

🟡 Spring Boot / Backend Questions

Q8. Explain the layered architecture of your backend.
I followed the standard Spring Boot layered architecture. Controllers handle HTTP requests, validate input, and return responses — they contain no business logic. Services contain all business logic — InterrogationService builds the AI prompt, calls OpenAI, persists messages. Repositories are Spring Data JPA interfaces that handle all SQL — I just declare method names like findBySessionIdAndCharacterId and Spring generates the query. Models are JPA entities that map to database tables. DTOs are plain data objects used to transfer data between layers without exposing internal models. This separation makes each layer independently testable and maintainable.
Q9. How does the WebSocket implementation work?
I used Spring's STOMP over SockJS. The frontend connects to /ws and subscribes to a topic: /topic/interrogate/{sessionId}/{characterId}. When the player sends a message it goes to /app/interrogate which routes to the @MessageMapping method in InterrogationWebSocketController. The controller immediately pushes a "typing" event to the topic, then calls the interrogation service which takes 1-3 seconds to get the AI reply, then pushes the actual reply. The frontend shows bouncing dots while waiting — this gives a real-time feel rather than the page just freezing during the API call.
Q10. How do you call the OpenAI API from Spring Boot?
I use Spring WebFlux's WebClient which is the modern non-blocking HTTP client. I build a JSON body using Jackson's ObjectNode containing the model name, temperature, max tokens, and a messages array with the system prompt and conversation history. I make a POST request to api.openai.com/v1/chat/completions with the Authorization: Bearer header containing the API key. The response is parsed to extract choices[0].message.content. I chose WebClient over RestTemplate because it's the recommended approach in Spring Boot 3 and supports reactive programming if needed.
Q11. How do you handle errors in the backend?
I have a GlobalExceptionHandler annotated with @RestControllerAdvice that catches exceptions at the application level. IllegalArgumentException returns 400 Bad Request, IllegalStateException returns 409 Conflict, and RuntimeException returns 500 Internal Server Error. Each controller also has local try-catch for expected failures like an invalid character ID or evidence not yet available. On the frontend, Axios calls are wrapped in try-catch and if the backend is unreachable the game falls back to client-side logic so the frontend is always playable.

🔴 Database Questions

Q12. Why did you choose MySQL over something like MongoDB?
The data in this game is highly relational. A session has many evidence items, many conversation messages, many notes — all with foreign key relationships. MySQL enforces referential integrity: if a session is deleted, all its evidence, messages, and notes cascade delete automatically. The data structure is well-defined and consistent, which suits a relational model. MongoDB would be appropriate if the data structure was variable or document-oriented, but here we always know exactly what fields each entity has.
Q13. What is the unique constraint on collected_evidence and why does it matter?
UNIQUE KEY uq_session_evidence(session_id, evidence_id) prevents a player from collecting the same evidence item twice. Without it, rapid clicks or retry API calls could insert duplicate rows. The service layer also checks existsBySessionIdAndEvidenceId before inserting, but the database constraint is the true safety net. Defense in depth — never rely on application code alone for data integrity, enforce it at the database level too.
Q14. What is the leaderboard view and how does it work?
It's a MySQL VIEW — a saved query that behaves like a virtual table. It selects from game_sessions where phase is SOLVED and is_correct_accusation is TRUE, ordered by elapsed_seconds ascending. A view doesn't store data — it runs the query each time you SELECT from it. This means the leaderboard is always up to date. I used a view instead of a separate table to avoid data duplication and keep the schema clean.

🟣 AI / LLM Questions

Q15. How do you make the AI characters stay in character and not reveal everything at once?
Through careful prompt engineering. Each character's system prompt explicitly states what they know, what they're hiding, and how they should behave at each stage. For example, Sam Carter's prompt says "first deny the 2AM server access entirely, then when shown the server access logs, claim it was scheduled maintenance, then if pressed very hard with the Dana Voss email, crack slightly." The prompt also instructs the character never to break character and never say they are an AI. The backend also injects context about what evidence the player has collected, so the character knows what the player knows and can respond accordingly.
Q16. What is temperature in OpenAI API and what value did you use?
Temperature controls how random/creative the AI's responses are. 0 means deterministic — the same input always gives the same output. 1 means highly creative but potentially inconsistent. I used 0.85 — high enough that each conversation feels unique and the character has personality, but low enough that they don't go completely off-script or contradict their established secrets. For a game where consistency matters, anything above 0.9 risks the character accidentally revealing too much or breaking the narrative.
Q17. How do you prevent the AI from running up huge API costs?
Three ways: (1) max_tokens is set to 300, so each response is short and concise — this directly limits cost per call. (2) Conversation history is capped at the last 10 turns — sending a 50-turn history would multiply token costs significantly. (3) The system prompt is dynamically built but kept concise — it includes only the relevant evidence context rather than dumping all game data. In a production version I'd also add rate limiting per session and a maximum interrogation turn count.
Q18. What would you improve if you had more time?
Several things: (1) Streaming responses — OpenAI supports streaming so the character's reply could appear word by word in real time instead of all at once, which would feel much more alive. (2) Multiple cases — the architecture supports it, I'd just add more character sets, evidence chains, and system prompts. (3) Difficulty levels — easy mode gives more analysis hints, hard mode removes them. (4) A real leaderboard page showing the fastest solves. (5) Voice — using the OpenAI TTS API to give each character a unique voice during interrogation. (6) Security — adding JWT authentication so sessions are properly secured.

🔵 System Design Questions

Q19. How would you scale this to handle 1000 concurrent players?
The main bottleneck is the OpenAI API calls — each interrogation takes 1-3 seconds and is synchronous in the current design. I'd switch to async processing: accept the interrogation request, queue it with something like RabbitMQ or Kafka, process it in background workers, and push the result via WebSocket. On the database side I'd add connection pooling with HikariCP (Spring Boot uses it by default), add an index on session_id for all tables, and potentially add Redis caching for session state to reduce database reads. For horizontal scaling I'd containerise with Docker and use Kubernetes for orchestration, with a shared MySQL cluster.
Q20. Why store conversation history in MySQL instead of just keeping it in React state?
React state is ephemeral — if the player refreshes the page or closes the tab, everything is lost. Storing conversations in MySQL means: (1) sessions are resumable — the player can continue where they left off, (2) the data can be analysed — which questions do players ask most, which characters do they interrogate longest, (3) it's the source of truth for the backend when building AI context — I can reconstruct the full conversation from the database rather than trusting the frontend to send accurate history. Trust the database, not the client.
